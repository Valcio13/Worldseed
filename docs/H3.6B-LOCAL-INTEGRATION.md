# H3.6B Local End-to-End Integration Report

Date: 2026-10-16
Environment: disposable Hardhat chain (`743111`), isolated Wrangler Pages Functions process, and a fresh local D1 database. The repository `.dev.vars` file was not read or modified.

## Result

The isolated candidate-service and local V2 expedition smoke path passed. The harness generated a disposable player key and attester key at runtime, funded the player from the local Hardhat owner, and passed the attester address to both the local contract deployment and the temporary Pages process. Private keys were never printed or persisted to tracked files.

The local-only reset route used by the harness was confined to the temporary Wrangler copy and only clears that run's challenge-rate-limit tables. Production rate limiting and source validation were unchanged.

## Verified path

The run verified:

- genuine ETH Sepolia, Hemi Sepolia, and Bitcoin Testnet4 source records through the existing adapters;
- confirmation thresholds and provenance fields on all three candidate records;
- candidate persistence and refresh/concurrent idempotency in D1;
- EIP-712 candidate signature recovery to the contract attester;
- selection locking and rejection of a changed selection;
- wrong-wallet rejection;
- local V2 deployment with `attester()` equal to the candidate-service signer;
- selected seed parity between the preview candidate and `expeditionState`;
- successful first expedition start and abandonment;
- a new candidate set and successful second expedition start after abandonment.

The selected first candidate source was Ethereum. The first and second candidate commitments differed.

## Failure and recovery coverage

The run covered wrong-wallet rejection, candidate reselection rejection, provider retry behavior, and the known Bitcoin coinbase-only block response (the harness retries boundedly). Reverted receipt handling is covered by the existing frontend and contract regression suites, but was not forced through a browser wallet in this run. Expired-attestation renewal, wrong-chain/wrong-contract signatures, backend restart during a pending request, and reload during a pending wallet transaction remain manual or follow-up checks.

## Browser status

No wallet-enabled browser automation was available in this environment. HTTP/API and local-chain success must not be treated as browser verification. The three-preview UI, wallet signature prompts, transaction feedback, abandonment confirmation, and reload recovery still require a disposable funded wallet in a real browser.
